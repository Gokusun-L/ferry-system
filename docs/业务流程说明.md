# 核心业务流程与规则说明

> 目的：把散落在 Service、Mapper、定时任务里的业务规则集中说明，读代码前先建立全局认识。
> 版本：v1.0　日期：2026-11-26　对应代码：`main` 分支
> 配套文档：`docs/需求清单.md`（需求到代码的对照）、`docs/接口契约.md`（前后端接口）、`docs/ER模型与关系模式设计.md`（表结构）

## 1. 系统总览

系统只有一条主业务链：**班次开售 → 选座锁定 → 下单 → 支付 → 检票**，围绕它派生退票、改签、班次取消三条逆向链路。

```
查询班次(SELLING)
   │
   ├─ 选座 ──> schedule_seat: AVAILABLE → LOCKED (5 分钟)
   │                              │
   │ 下单                         ├─ 用户取消/超时 ──> AVAILABLE
   │                              ▼
   └──────────────> orders(UNPAID) + ticket(UNPAID) + seat(LOCKED, 绑定订单)
                         │
                         ├─ 5 分钟未支付 ──> 定时任务取消订单，释放座位
                         │
                         └─ 支付 ──> orders(PAID) + ticket(PAID) + seat(SOLD)
                                        │
                                        ├─ 检票 ──> ticket(CHECKED) ──> 班次完成 ──> orders(FINISHED)
                                        ├─ 退票 ──> ticket(REFUNDED) + seat(AVAILABLE)
                                        └─ 改签 ──> 旧票(RESCHEDULED) + 新票(PAID)，补/退差价
```

三个角色看到的入口不同，但共用同一套业务表和状态机：

| 角色 | 页面入口 | 可做的事 | 数据范围 |
|---|---|---|---|
| 管理员 ADMIN | `/admin/*` | 用户、航线、船舶、班次、订单、统计 | 全量 |
| 售票员 SELLER | `/seller/*` | 线下售票、检票、退票、个人业绩 | 仅本人售出订单与个人业绩 |
| 乘客 PASSENGER | `/passenger/*` | 查询、购票、支付、退改签、我的船票 | 仅本人订单与船票 |

权限实现：`LoginInterceptor` 负责登录态（API 返回 401 JSON，页面跳登录页）；`RoleInterceptor` 读取 `@RequireRole`（接口 403，页面回首页）；订单、票、业绩等资源在 Service 层再做归属校验。系统没有引入 Spring Security 过滤器链，只使用其 `BCryptPasswordEncoder`。

## 2. 班次生命周期

### 2.1 状态机

```
            发布(publish)              到发船时间(定时任务)
PENDING ─────────────────> SELLING ─────────────────────> DEPARTED
   │                          │                                │
   │ 取消(cancel)             │ 取消(cancel)                    │ 到到达时间(定时任务)
   ▼                          ▼                                ▼
CANCELLED <───────────────────┘                            FINISHED
```

| 状态 | 含义 | 进入方式 | 能否编辑 | 能否取消 |
|---|---|---|---|---|
| `PENDING` | 待发布 | 新建/批量生成 | 可以（无订单时） | 可以 |
| `SELLING` | 售票中 | 管理员发布，且发船时间必须在未来 | 可以（无订单时） | 可以 |
| `DEPARTED` | 已发船 | 定时任务每分钟把到点的 `SELLING` 班次推进 | 不可以 | 不可以 |
| `FINISHED` | 已完成 | 定时任务每分钟把已到到达时间的 `DEPARTED` 班次推进 | 不可以 | 不可以 |
| `CANCELLED` | 已取消 | 管理员取消 | 不可以 | 不可以 |

实现位置：`ScheduleServiceImpl.publish/cancel/update/delete`、`ScheduledTask.departSellingSchedules/finishDepartedSchedules`。

### 2.2 新建与批量生成

- 到达时间由服务端计算：`arrive_time = depart_time + route.duration`，不接收前端传入。
- 创建成功后立即按船舶座位模板初始化 `schedule_seat`，全部为 `AVAILABLE`。
- 批量生成每天同一时刻一条，单次最多 90 天；与已有班次时间冲突的日期直接跳过，不报错中断。
- 船舶时间冲突判定：同一 `ship_id`、未删除、状态为 `PENDING/SELLING`，且时间区间重叠。已发船、已完成、已取消的班次不参与冲突判断。
- 航线唯一性按“出发港 + 到达港 + 航线名称”三字段组合判断。

### 2.3 编辑与删除限制

| 操作 | 允许条件 | 拒绝提示 |
|---|---|---|
| 编辑班次 | 状态为 `PENDING/SELLING`，且无未完成订单（`UNPAID/PAID/CHECKED`） | “班次已发船，不允许修改”“该班次已产生订单，不允许修改” |
| 删除班次 | 无未完成订单 | “该班次有未完成订单，请先取消班次” |
| 删除航线/船舶 | 无未完成班次 | “该航线下有未完成班次/该船舶有未完成班次，不允许删除” |
| 换船 | 仅限无订单的 `PENDING/SELLING` 班次；删除旧班次座位并按新船重建 | 有订单时已被编辑限制拦截 |
| 修改船舶座位数 | 该船舶尚无任何班次 | “该船舶已有班次，不能修改总座位数” |

航线和船舶均使用逻辑删除（`deleted=1`），不做物理删除；查询、冲突校验、统计均过滤 `deleted=1`。

## 3. 座位三态与锁定

### 3.1 两张座位表

| 表 | 作用 | 关键字段 |
|---|---|---|
| `ship_seat` | 船舶模板：这艘船有哪些座位 | `ship_id + seat_no` 唯一，`row_no/col_no` |
| `schedule_seat` | 班次实例：某个班次每个座位当前状态 | `schedule_id + seat_no` 唯一，`status/order_id/lock_time/lock_user_id` |

班次创建时把 `ship_seat` 复制成 `schedule_seat`。之后所有售票状态只改 `schedule_seat`，不再改模板表。

### 3.2 三种状态

| 状态 | 含义 | 谁写入 | 释放条件 |
|---|---|---|---|
| `AVAILABLE` | 可售 | 初始化、退票、取消订单、改签、取消班次、锁超时 | - |
| `LOCKED` | 已锁定 | 选座、下单 | 本人取消选座、5 分钟超时、订单取消、支付失败回滚 |
| `SOLD` | 已售 | 支付成功、改签新票 | 退票、改签旧票、取消班次 |

### 3.3 选座即锁

```
点击座位 → POST /api/seats/lock
        → UPDATE schedule_seat
          SET status='LOCKED', lock_time=NOW(), lock_user_id=当前用户
          WHERE schedule_id=? AND seat_no=?
            AND (status='AVAILABLE'
                 OR (status='LOCKED' AND lock_user_id=当前用户))
```

- 条件更新保证并发下只有一个请求成功；返回 0 时区分“座位不存在 / 已售 / 他人锁定”给出提示。
- 同一用户再次点击已锁座位会调用 `unlock`，仅能释放“自己锁定且尚未绑定订单”的座位。
- 选座上限 5 个，座位号不得重复。
- 下单成功后座位绑定 `order_id`；此时本人也不能再通过 `unlock` 释放，只能取消订单或等待超时。

### 3.4 时间线与释放

```
t0        选座              LOCKED (order_id=NULL, lock_user_id=U, lock_time=t0)
t0+几秒   提交订单          LOCKED (order_id=O, lock_time=下单时间)
t0+5min   未支付            定时任务取消订单 → ticket=CANCELLED → 座位 AVAILABLE
t0+5min   已支付            LOCKED → SOLD，lock_time 清空
```

- 定时任务每 30 秒执行 `releaseExpiredLocks`，释放 `LOCKED` 且 `lock_time` 超过 5 分钟的座位。
- 支付接口同时校验“订单创建时间 + 5 分钟”，超时直接拒绝支付，避免和定时任务竞争。
- 座位图接口会为前端补 `lockExpireTime = lock_time + 5 分钟`，用于展示倒计时。

## 4. 下单与支付

### 4.1 下单时序

`POST /api/orders` → `OrderServiceImpl.createOrder`

1. **身份判定**：会话角色为 `PASSENGER` 时写 `user_id`，否则写 `seller_id`，渠道分别为 `ONLINE/OFFLINE`；不信任请求体里的身份字段。
2. **锁定班次行**：`SELECT ... FOR UPDATE` 锁 `schedule` 行，串行化同一班次的重复购票校验与座位锁定。
3. **校验班次**：必须存在、未删除、状态为 `SELLING`。
4. **校验票数与座位**：1~5 张；座位号不重复；同一订单身份证号不重复。
5. **校验乘客信息**：姓名非空；身份证 `^\d{17}[\dXx]$`；手机号 `^1[3-9]\d{9}$`。
6. **一人一班次一票**：按 `schedule_id + id_card` 统计状态为 `UNPAID/PAID/CHECKED` 的票，大于 0 拒绝。
7. **创建订单**：`order_no = O + 毫秒时间戳 + 3 位序列`，状态 `UNPAID`，总价 = 班次票价 × 票数。
8. **锁定座位并生成票**：逐张条件更新座位为 `LOCKED` 并绑定订单；任一失败抛异常，整个事务回滚。票号 `T + 毫秒时间戳 + 3 位序列`，状态 `UNPAID`。

### 4.2 支付

`POST /api/orders/{id}/pay` → `OrderServiceImpl.pay`

- 校验订单存在、状态 `UNPAID`、操作人是下单人或售票员。
- 校验班次仍在 `SELLING`、未超过 5 分钟支付时限。
- 条件更新订单为 `PAID` 并写 `pay_time`；若影响行数为 0，说明已被取消或重复支付。
- 逐张票：座位必须仍为 `LOCKED` 且 `order_id` 匹配，改为 `SOLD`；票状态条件更新 `UNPAID → PAID`；班次 `sold_count + 1`。
- 任一步失败整体回滚，不会出现“订单已支付但座位没卖”的半状态。

### 4.3 失败分支

| 场景 | 结果 |
|---|---|
| 班次非售票中 | 拒绝下单/支付 |
| 座位被他人锁定或已售 | 返回具体座位原因，事务回滚 |
| 同一身份证已买该班次 | 拒绝下单 |
| 超过 5 分钟未支付 | 支付接口拒绝；定时任务每 30 秒取消订单并释放座位 |
| 并发支付同一订单 | 条件更新只有一笔成功，另一笔提示状态已变更 |
| 待支付订单主动取消 | 票置 `CANCELLED`，座位释放，订单置 `CANCELLED` |

## 5. 一人一班次一票

规则：一个身份证号在同一班次只能持有一张有效票。

- “有效”指票状态为 `UNPAID / PAID / CHECKED`。
- 已退票、已取消、已改签作废的票不占用名额，可以重新购买。
- 同一订单内也校验身份证不重复。
- 并发下单时，两个请求会先竞争同一班次的行锁，后到者在前者提交后重新统计，从而看到已存在的票。
- 改签同样在目标班次行锁内校验“目标班次是否已有该身份证的有效票”。

## 6. 退票

### 6.1 规则

| 条件 | 结果 |
|---|---|
| 班次已发船 | 不可退 |
| 订单含已检票票 | 不可退 |
| 订单含未支付票 | 不可退 |
| 发船前 ≥ 120 分钟 | 全额退款，手续费 0 |
| 发船前 < 120 分钟 | 每张票收取票价 20% 手续费，四舍五入到分 |
| 无 `PAID` 票 | 不可退 |

权限：

- 管理员：任意订单。
- 售票员：仅自己售出的订单（`orders.seller_id = 当前用户`）。
- 乘客：仅本人订单（`orders.user_id = 当前用户`）。

### 6.2 处理步骤（同一事务）

1. 计算距发船分钟数，确定手续费率。
2. 逐张 `PAID` 票：
   - 条件更新 `PAID → REFUNDED`；
   - 按 `order_id + seat_no` 释放座位为 `AVAILABLE`；
   - 班次 `sold_count - 1`；
   - 写 `refund` 记录：退款金额、手续费、原因、操作人、`biz_type=REFUND`。
3. `recalcOrderStatus` 重算订单状态（全部票退完则订单为 `REFUNDED`）。
4. 写站内通知 `REFUND_SUCCESS`。

退票原因由前端提示输入，允许为空；统计时为空归为“未填写”。

## 7. 改签

### 7.1 规则

| 条件 | 说明 |
|---|---|
| 原票状态 | 必须 `PAID`，已检票、已退票、已改签均不可 |
| 操作人 | 必须是订单所属乘客；管理员/售票员接口层面不开放改签 |
| 目标班次 | 必须不同于原班次、状态 `SELLING`、尚未发船 |
| 原班次时间 | 距发船必须大于 1 小时 |
| 一人一票 | 目标班次不能已有该身份证的有效票 |
| 目标座位 | 必须可锁（`AVAILABLE` 或本人锁定） |

### 7.2 处理步骤（同一事务）

1. 校验原票、订单归属、目标班次与时间。
2. 对目标班次行 `SELECT ... FOR UPDATE`，串行化目标班次的重复购票校验与锁座。
3. 校验目标班次无同身份证有效票。
4. 条件锁定目标座位并绑定原订单。
5. 原票 `PAID → RESCHEDULED`（不是 `REFUNDED`，避免统计把改签算成退票）。
6. 释放原座位，原班次 `sold_count - 1`。
7. 生成新票：沿用乘客姓名/身份证/手机号，票价取新班次票价，状态直接 `PAID`；目标座位置 `SOLD`；新班次 `sold_count + 1`。
8. 写 `reschedule` 日志：原/新票、原/新班次、差价 `price_diff = 新票价 - 原票价`。
9. 差价结算：
   - `price_diff < 0`：写 `refund` 记录，退款金额为差价绝对值，`biz_type=RESCHEDULE_DIFF`；
   - `price_diff > 0`：记录在日志中，并随订单有效金额重算体现为应补金额。
10. `recalcOrderStatus` 重算订单金额与所属班次；写通知 `RESCHEDULE`。

说明：系统是模拟支付体系，正向差价没有独立收款流水，只有 `reschedule.price_diff` 与订单金额变化；负向差价则真实写入退款记录但不计入退票统计。

## 8. 班次取消与自动退票

`POST /api/schedules/{id}/cancel` → `ScheduleServiceImpl.cancel`

允许取消 `PENDING/SELLING`；已发船、已完成、已取消均拒绝。整个过程在一个事务内：

1. 找出该班次票状态为 `PAID/CHECKED` 的订单 ID 集合。
2. 对每个订单执行 `refundForCancellation`：
   - 每张 `PAID/CHECKED` 票条件更新为 `REFUNDED`；
   - 释放座位、班次 `sold_count - 1`；
   - 写 `refund`：全额退款、手续费 0、原因“班次取消自动退票”、`biz_type=REFUND`；
   - 重算订单状态；
   - 写通知 `SCHEDULE_CANCEL`，告知订单号与退款金额。
3. 未支付票：`UNPAID → CANCELLED`，释放座位，记录订单 ID 待重算。
4. `releaseAllBySchedule` 清空该班次所有非 `AVAILABLE` 座位，防止残留锁定。
5. 班次状态置 `CANCELLED`。
6. 对未支付票涉及的订单重算状态。

注意：已检票的票在班次取消时同样全额退款，这是“取消班次”与普通退票的差异。

## 9. 检票

`POST /api/checkin` → `OrderServiceImpl.checkIn`

支持两种输入：

- **船票编号**：定位单张票后校验。
- **订单号**：过滤掉 `CANCELLED/REFUNDED/RESCHEDULED` 的票，剩余票必须全部为 `PAID`，逐张检票；只要有一张不是 `PAID` 就整单拒绝。

单张票校验顺序与提示：

| 校验 | 失败提示 |
|---|---|
| 票状态不是 `PAID` | 已检票 / 已退票 / 已改签，请使用新票 / 已取消 / 未支付不可检票 |
| 选择了班次但与票不匹配 | 该票不属于所选班次 |
| 当前时间超过“发船时间 + 2 小时” | 该票已过期 |
| 条件更新失败 | 船票状态已变更，请刷新后重试 |

成功后写 `check_time`、`checker_id`，票状态 `PAID → CHECKED`，并重算订单状态。

检票统计不单独建表：按班次查询票明细后，前端统计“总售票 = 已支付 + 已检票”“已检票 = CHECKED”“未检票 = 总售票 - 已检票”。

## 10. 状态推导

### 10.1 船票状态

| 状态 | 含义 |
|---|---|
| `UNPAID` | 已下单未支付 |
| `PAID` | 已支付待检票 |
| `CHECKED` | 已检票 |
| `REFUNDED` | 已退票 |
| `CANCELLED` | 订单取消/班次取消导致作废 |
| `RESCHEDULED` | 因改签作废，已有新票替代 |

### 10.2 订单状态由票推导

`OrderServiceImpl.recalcOrderStatus` 是唯一入口，每次票状态变化后调用：

| 有效票情况 | 订单状态 |
|---|---|
| 存在有效票，且全部 `CHECKED`，班次已完成 | `FINISHED` |
| 存在有效票，且全部 `CHECKED`，班次未完成 | `CHECKED` |
| 存在有效票，至少一张 `PAID` | `PAID` |
| 存在有效票，全部 `UNPAID` | `UNPAID` |
| 无有效票，存在 `REFUNDED` | `REFUNDED` |
| 无有效票，存在 `CANCELLED` | `CANCELLED` |

有效票 = `UNPAID/PAID/CHECKED`。同时订单的 `total_amount` 和 `schedule_id` 会按有效票重算：金额为有效票票价之和；若有效票都在同一班次，订单班次随之更新（改签后订单会指向新班次）。

班次完成时，`ScheduledTask.finishDepartedSchedules` 会把该班次已检票订单批量置为 `FINISHED`。

## 11. 统计口径

所有统计以“票”为最小单位，不以订单为单位。核心口径如下：

| 指标 | 口径 |
|---|---|
| 售票量/售票金额 | 票状态 `PAID/CHECKED`，时间取订单 `pay_time` |
| 退票量/退票金额 | `refund.refund_time` 在区间内，且 `biz_type='REFUND'` |
| 改签差价退款 | `biz_type='RESCHEDULE_DIFF'`，不计入退票量和退票率 |
| 净收入 | 售票金额 - 退票金额（不含手续费抵扣） |
| 退票率 | 退票数 /（售票数 + 退票数）× 100% |
| 班次上座率 | 当前有效票数 / 船舶总座位数 × 100%，不直接使用 `sold_count` |
| 航线平均上座率 | 先算每个班次上座率，再对航线内班次求平均 |
| 早/午/晚班 | 发船小时 `<12` / `12-18` / `>=18` |
| 低上座率预警 | 上座率 `<50%`，仅统计 `SELLING/DEPARTED` 班次 |
| 班次售票/退票 | 按发船日期筛选；售票数为当前有效票，退票数为当前 `REFUNDED` 票 |
| 收入周期 | 按 `pay_time` / `refund_time` 分日、周（`%x-W%v`）、月 |

补充说明：

- 统计接口全部在 `StatsMapper.xml` 中用 `SUM/COUNT/AVG/CASE WHEN/GROUP BY/HAVING` 完成。
- `schedule.sold_count` 只用于页面余座展示，支付、退票、改签、取消时同步增减；统计和上座率会从票表重新聚合，避免计数漂移影响报表。
- 班次统计的退票数是“当前状态为已退票”的票，不是“区间内发生退票”的票；按时间口径的退票分析请使用 `/api/stats/by-date`、`/api/stats/refund`。

## 12. 并发与一致性设计

| 机制 | 位置 | 解决的问题 |
|---|---|---|
| 班次行锁 `SELECT ... FOR UPDATE` | `ScheduleDao.findByIdForUpdate` | 同一班次的“一人一票”校验与座位锁定串行化 |
| 座位条件更新 | `ScheduleSeatMapper.lock` | 两个请求同抢一个座位，只有一个 `UPDATE` 影响 1 行 |
| 座位售出条件更新 | `ScheduleSeatMapper.markSold` | 只有“自己订单锁定的座位”才能置为已售 |
| 票状态条件更新 | `TicketMapper.updateStatusIf`、`markChecked` | 防止重复支付、重复退票、重复检票 |
| 订单状态条件更新 | `OrderMapper.markPaid`、`cancelIfUnpaid` | 支付与超时取消竞争时只有一方成功 |
| 唯一索引 | `uk_order_no`、`uk_ticket_no`、`uk_schedule_seat` | 应用层失效时的最后一道数据库防线 |
| 定时任务 + 条件更新 | `ScheduledTask` | 超时订单与超时座位锁的最终释放，且不会误伤已支付数据 |
| 事务边界 | `@Transactional` | 订单、票、座位、退款、日志、通知要么全成功要么全回滚 |

设计取舍：优先使用数据库条件更新而不是应用层锁，原因是多实例部署时 JVM 锁失效，而数据库约束和行锁仍然有效。

## 13. 消息通知

| 类型 | 触发点 | 接收人 |
|---|---|---|
| `SCHEDULE_CANCEL` | 班次取消且订单产生退款 | 下单乘客 |
| `REFUND_SUCCESS` | 普通退票成功 | 下单乘客 |
| `RESCHEDULE` | 改签成功 | 下单乘客 |

- 通知与业务写在同一事务内，业务回滚则通知不产生。
- 顶部铃铛轮询 `GET /api/notifications/unread-count`；通知页支持分页与全部已读。
- 线下代购订单若 `user_id` 为空，不发送站内通知（没有接收账号）。

## 15. 已知边界

| 项目 | 现状与影响 |
|---|---|
| 支付 | 模拟支付，没有支付流水表与第三方网关；支付成功即视为收款完成 |
| 改签正向差价 | 只记录 `price_diff` 并重算订单金额，没有独立收款记录 |
| 单号生成 | 进程内序列，单实例可靠；集群部署需换雪花算法或数据库序列 |
| 检票过期展示 | 后端允许发船后 2 小时内检票，页面在发船时间后即显示“已过期” |
| 二维码/打印 | 二维码为占位块，打印调用浏览器打印 |
| 售票员退票范围 | 只允许退自己售出的订单，这是数据隔离要求下的有意限制 |
| 旧库升级 | 旧环境需执行 `sql/03_migration_1_1.sql` 增加通知表与座位锁字段 |

更细的字段、约束与索引见 `sql/01_schema.sql` 和 `docs/ER模型与关系模式设计.md`；接口参数与返回结构见 `docs/接口契约.md`。
