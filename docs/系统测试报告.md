| 测试库 | `ferry_test`（与演示库 `ferry_db` 隔离，结构与约束完全一致） |

### 测试方法

1. **集成测试而非单元测试**：全部用例连接真实 MySQL，不使用 H2 等内存库。原因是本项目考核重点是**外键约束、CHECK 约束、行级锁、FOR UPDATE、事务回滚**，这些在内存库中语义不同，测不出真实问题。
2. **事务隔离**：单线程业务用例继承 `BaseIntegrationTest`，测试方法加 `@Transactional`，执行后自动回滚，用例之间互不污染。
3. **并发用例特殊处理**：并发测试不能包在单个事务里（否则线程看不到彼此的提交），因此独立为 `ConcurrencyTest`，用 `JdbcTemplate` 真实落库，测试后**保留数据**作为报告证据。
4. **测试数据构造**：所有订单均使用库中真实存在的用户（`orders.user_id` 有外键约束），避免"测试通过但数据非法"的假阳性。

### 5.4.3 一致性实现说明

| 并发场景 | 实现手段 | 为什么这样做 |
|---|---|---|
| 抢同一座位 | `UPDATE schedule_seat SET status='LOCKED' WHERE schedule_id=? AND seat_no=? AND status='AVAILABLE'`，判断受影响行数 | 用 SQL 的原子条件更新代替"先查后改"。先查后改在两个事务间存在时间窗，必然超卖；条件更新由 InnoDB 行锁保证互斥 |
| 一人一班次一票 | 下单前 `SELECT ... FROM schedule WHERE id=? FOR UPDATE` 锁班次行，再校验身份证 | 同一身份证并发下单时，"校验-插入"必须是原子的。锁班次行把同班次下单串行化，校验才可信。代价是同班次下单吞吐下降，但保证正确性 |
| 并发支付 | `UPDATE orders SET status='PAID' WHERE id=? AND status='UNPAID'` | 条件更新天然幂等，第二次支付影响 0 行直接拒绝，避免重复加 sold_count |
| 座位锁超时 | `lock_time` 字段 + 定时任务 `UPDATE ... WHERE status='LOCKED' AND lock_time < NOW()-5min` | 用状态校验而非内存定时器，应用重启不丢锁；批量 UPDATE 一次释放，避免逐条处理 |
| 取消班次退票 | 整个 `cancel()` 包在 `@Transactional`，内部逐单调用退票 | 班次状态、订单状态、座位、退款、通知五张表必须同生共死，任一失败全部回滚 |

```
              content='您订单 O2026... 所在班次已取消，票款 ¥100.00 已全额退还'
```

## 5.6 测试中发现并修复的缺陷

测试过程中发现 4 个真实缺陷，均已定位根因并修复，修复后补充或修正了对应回归用例。

### 缺陷 1：订单号/船票号生成存在碰撞，高并发下单直接失败

| 项 | 内容 |
|---|---|
| 现象 | 测试执行到第 4 轮时报 `DuplicateKeyException: Duplicate entry 'O202611241544085046' for key 'orders.uk_order_no'`，下单失败 |
| 根因 | 单号格式为 `"O" + yyyyMMddHHmmss（秒级） + 4 位随机数`。同一秒内随机值只有 9000 种，按生日悖论在数十次下单内即发生碰撞；撞上唯一约束即抛异常。这不是偶发，而是熵不足的必然 |
| 影响 | 售票高峰同一秒数十单时，用户会随机遇到"下单失败"，且报错为数据库异常而非业务提示 |
| 修复 | 改为 `前缀 + yyyyMMddHHmmssSSS（毫秒级） + 3 位进程内自增序列`。同一毫秒内 1000 单以内严格不重复；进程内序列由 `AtomicInteger` 保证 |
| 遗留限制 | 集群部署时进程内序列不共享，需改用雪花算法或数据库序列（已在代码注释中标注） |
| 回归用例 | TC-O17：连续 40 次下单，断言 40 个订单号与 40 个船票号互不重复 |

### 缺陷 2：座位锁定失败的提示不区分原因

| 项 | 内容 |
|---|---|
| 现象 | 传入不存在的座位号（如 8 座船的 4A）时，提示"座位 4A 已被占用"，与实际原因不符 |
| 根因 | `lock()` 返回受影响行数 0 有两种可能：座位在该班次不存在、座位被他人锁定/已售。原实现把两种情况合并成同一句提示 |
| 影响 | 用户看到"已被占用"会反复重试不存在的座位；运维排查时无法从提示区分是数据问题还是并发问题 |
| 修复 | 新增 `seatLockFailureReason()`：锁定失败后回查座位，区分"不存在"「已售出」「已被他人锁定」三种提示 |
| 回归用例 | TC-O03、TC-O13 的断言同步改为校验具体提示语 |

### 缺陷 3：航线唯一性校验粒度小于任务书要求

| 项 | 内容 |
|---|---|
| 现象 | 代码扫描阶段发现 `countSameRoute()` 只比较「出发港 + 到达港」，任务书要求「出发港口、到达港口和航线名称的组合」 |
| 根因 | 实现时按两元组建的唯一性判断，比要求更严格 |
| 影响 | 同一对港口只能建一条航线，无法并存"市区-海岛快线"与"市区-海岛慢线"，误伤正常业务 |
| 修复 | DAO 与 Mapper 增加 `routeName` 参数，改为三元组判断 |
| 回归用例 | TC-R02：三元组重复被拒 + 同港口不同航线名允许创建 |

### 缺陷 4：改签被算成退票，退票量与退票率虚高

| 项 | 内容 |
|---|---|
| 现象 | 把 1 张票从班次1改签到班次2后，班次1 的「退票量」由 2 变成 3，但实际没有任何人退票；收入汇总的退票笔数同样多出 1 笔。若改签到票价更低的班次，还会有一笔「改签退还差价」出现在「退票原因分布」里 |
| 根因 | `ticket.status` 与 `refund` 表都被复用承载了两类不同业务事实。改签的实现是「旧票作废 + 新开一张票」，旧票被置成 `REFUNDED`，与真实退票共用同一取值；改签退还的差价也写进 `refund` 表且没有类型字段。而 `statsBySchedule` 按 `t.status='REFUNDED'` 聚合、`incomeSummary`/`refundStats`/`statsByDate` 按 `refund` 全表聚合，于是改签被无差别计入退票。这是「一个字段承担两个语义」造成的统计污染，不是某条 SQL 写错 |
| 影响 | 退票量、退票率、退票损失、退票原因分布四项指标全部虚高。退票率属于管理决策指标，虚高会误导对航线服务质量的判断 |
| 修复 | ①`ticket.status` 增加独立取值 `RESCHEDULED`，改签时旧票置为该状态，不再复用 `REFUNDED`；②`refund` 表增加 `biz_type`（`REFUND` / `RESCHEDULE_DIFF`），改签差价退款打独立标记；③四处退款聚合统一追加 `biz_type='REFUND'` 过滤；④提供 `04_migration_1_2.sql` 增量升级，并从 `reschedule.old_ticket_id` 回填历史改签票 |
| 备选方案与否决理由 | 只在统计 SQL 里排除 `reschedule.old_ticket_id` 改动更小，但状态语义仍然重载，任何新增的按 `REFUNDED` 聚合都会再踩一次同样的坑，属于打补丁而非治因，故否决 |
| 回归用例 | TC-ST07、TC-ST08；同时修正 TC-O12 对原票状态的断言 |

实测对照（`ferry_db` 班次1：2 张真退票 + 1 张改签作废）：

| 指标 | 修复前 | 修复后 | 真实值 |
|---|---|---|---|
| 班次1 退票量 | 3 | 2 | 2 |
| 收入汇总 退票笔数 | 4 | 3 | 3 |
| 收入汇总 退票损失 | 210.00 | 180.00 | 180.00 |

### 测试设计要点：MyBatis 一级缓存对测试的影响

编写 TC-O06（支付超时）时出现过"改了下单时间但支付没报超时"的现象。根因不在业务代码：同一测试事务内，MyBatis 一级缓存（SqlSession 级）会缓存首次 `findById` 的结果，改库后再次查询仍返回旧对象。生产环境每次请求是独立 SqlSession，不受影响。

处理方式：把一个测试方法里"预期失败的写操作"拆成独立用例（TC-O05/O06/O07），保证每个用例内订单只被首次读取，避免缓存干扰断言。这也说明测试用例的粒度应按"业务状态"切分，而不是把多条断言堆在一个方法里。

## 5.7 测试结论

1. 58 个用例全部通过，覆盖任务书五个功能模块与数据库考核要点（约束、CRUD、事务并发、聚合统计、权限隔离）。
2. 并发控制达到预期：20 线程抢同一座位仅 1 单成功、0 次死锁；同一身份证并发下单仅 1 单成功；并发支付仅 1 次生效且已售数只加 1。
3. 事务原子性得到验证：取消班次时订单、座位、退款、通知四类数据一致变更，无残留有效订单。
4. 数据一致性得到验证：各测试班次 `sold_count` 与实际 `SOLD` 座位数完全一致。
5. 测试暴露并修复了 4 个真实缺陷（单号碰撞、提示不准确、唯一性粒度不足、改签污染退票统计），其中单号碰撞影响生产可用性，统计口径污染影响管理决策，二者都不属于表面问题。
6. 剩余风险：并发用例的吞吐表现未做压测（`FOR UPDATE` 串行化同班次下单是有意的正确性取舍）；集群部署下单号生成需替换方案。
